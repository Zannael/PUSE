# Portable graphics packs

Graphics do not change save bytes. A pack is scoped to a registered ROM hash and
save profile, while its engine descriptor is independent of the save codec.
Extracted images, ROMs and personal packs must remain in ignored local directories.

## Import and use

- Web (both runtime modes): load the save, expand **Compatibility**, and choose
  **Import graphics from ROM**. A worker reads the ROM locally, checks its hash
  against the selected profile, and stores only the extracted pack in IndexedDB.
  Rejected imports leave the previous pack intact. **Remove browser pack** removes
  the browser pack. No server connection is used for browser extraction.
  Browser import requires HTTPS or localhost for the Web Crypto hash check.
- **Export graphics pack** creates a ZIP with `manifest.json`, `resources.tsv`
  and `assets/`. Extract that ZIP into the selected profile's directory below.
- Python/backend: the canonical extractor needs only the Python standard library:

  ```sh
  python3 romre/extract_graphics.py --rom /private/game.gba \
    --profile radical-red-4.1 \
    --out backend/local_artifacts/graphics/radical-red-4.1
  ```

  The output directory must be empty. The backend discovers packs there, or under
  `$PUSE_GRAPHICS_ROOT/<profile-id>/`. Its optional `/graphics/import-rom` endpoint
  extracts into server memory; unlike the browser import, this explicitly sends
  the ROM to the backend. Restarting the server clears memory imports. The DELETE
  `/graphics/resources` endpoint clears memory imports only, not installed files.
  The existing pipeline can run the same extractor with `--only graphics`, or
  include it alongside metadata extraction with `--graphics`. Its `icons/` output
  is ignored by Git and must be empty before extraction.
- Switch: `sdmc:/switch/puse/graphics/<profile-id>/`.
- 3DS: `sdmc:/3ds/puse/graphics/<profile-id>/`.
- Both consoles also accept `romfs:/graphics/<profile-id>/`. SD takes precedence.
  Install SD packs before starting the app; restart after replacing a pack.
  The console builds consume extracted PNG packs; on-device ROM extraction is
  not implemented. They require no networking, ROM access, or decompression library.
  The lite Switch build can use an SD pack without embedding media in its NRO.

## Contract and coverage

Schema version 1 stores content-addressed RGBA PNGs (`assets/<sha256>.png`).
Manifest keys are `pokemon/<native-id>/<normal|shiny>/<front|back|icon>/<frame>`
and `items/<native-id>`. Native builds read the equivalent bounded TSV index;
its first line binds schema, profile and ROM hash to their generated registry.
Unsafe paths, unsupported schemas and mismatched profile/hash pairs are rejected.
Missing files fall back to shared assets or the existing empty/placeholder view.

Shiny status and gender come from each runtime's existing save reader, preserving
the profile's shiny threshold. Appearance metadata remaps female species and
Unown letters. Castform's four image/palette banks are exported; ordinary save
previews show frame 0. Menu icons use the original shared icon palettes, including
when the Pokémon is shiny. **Spinda's personality spots are not applied**: these
are generated by game code, rather than stored as individual sprites. Exporting
artwork is not a guarantee that every battle-dependent appearance is reproduced.

The three registered local binaries share the DPE reader. Iron Plate's `0x0A`
palette marker in Unbound is decoded using bounded BIOS-style LZ semantics. The
final LZ reference may extend beyond the logical resource size; the decoder
clips output to that declared size. It never edits or copies the input ROM.

Shared fallback indices are profile-specific. The generator uses unique exact
normalized names, omitting ambiguous duplicate names; no fuzzy or cross-ROM ID
matching is performed. Unbound's existing verified manifests remain supported.
Shared artwork may differ from the ROM and generally does not provide its shiny
palettes. The optional ROM pack supplies that fidelity.

## Adding a ROM

1. Verify the binary's identity, SHA-256 and engine. Inspect live table references,
   record counts, palette/frame layout and appearance rules; do not accept a
   decodable retained vanilla table as proof that it is the active table.
2. Add a descriptor to `backend/data/graphics/roms.json`. Reuse an engine when its
   layout matches. Exact hashes deliberately reject unverified game versions.
3. Add a new reusable reader/decoder only for a genuinely new mechanism, in the
   canonical Python implementation and browser port. For example, modern Emerald
   Expansion needs version/configuration-aware SpeciesInfo/ItemInfo layouts,
   raw palettes and potentially Smol decompression; changing offsets alone is
   insufficient. Other engine families have not been binary-tested here.
4. Generate mirrors with `python3 backend/tools/sync_graphics_data.py`, then run
   both ROMFS data sync scripts. This mirrors descriptors, fallback indices and
   the shared C++ pack reader; do not hand-edit generated copies.
5. Run `python3 backend/tools/graphics_regression.py --rom /private/game.gba`.
   This compares every Python/browser PNG's decoded pixels and resource keys,
   and tests both native readers on common corruption/appearance fixtures.
6. Adding graphics does **not** add save editing support. Register and verify
   save layouts/codecs separately before exposing a new editable game profile.

To regenerate shared fallback data intentionally:

```sh
python3 backend/tools/generate_graphics_fallbacks.py --pokemon-assets backend/icons/pokemon
python3 backend/tools/sync_graphics_data.py
switch-homebrew/scripts/sync_romfs_data.sh --data-only
3ds-homebrew/scripts/sync_romfs_data.sh
```

## Verification

`cd frontend && npm run graphics:regression` runs synthetic codec/error fixtures
and the two native pack readers. Private-ROM checks accept repeated `--rom`
arguments and never commit the inputs/outputs. Run the existing frontend parity
suite and all four native phases separately: those suites share temporary paths.
Run frontend lint/build and the Docker builds for both consoles after host tests.

Switch UI integration retains Plutonium's existing `MenuItem::SetIcon` and image
controls. References reviewed: Goldleaf `ui_Utils.cpp`, `ui_MainApplication.cpp`;
Plutonium `docs/files.html`, `docs/d6/d63/classpu_1_1ui_1_1elm_1_1_image.html`,
and `Plutonium/include/pu/ui/elm/elm_Menu.hpp`. No custom control or navigation
change was needed. 3DS uses its existing Starlight Image control for bag icons.
