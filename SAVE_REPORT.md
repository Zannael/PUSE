# Save health and change report

The browser's **Review / Download** action reads the loaded save and prepares an in-memory copy using the same reconciliation path as the eventual `.sav`/`.srm` download. The report itself neither changes the loaded save nor writes an output file. The user can cancel or download after reviewing it. The test suite verifies that previewed bytes equal the later downloaded bytes.

The report checks the active physical sector for each logical ID `0..13` (highest positive save index). It warns when a save is shorter than 28 sectors, an active logical section is absent, a checked active checksum is wrong, or the proposed output size differs from the upload. Section 0 uses a fixed `0xADC` checksum window and section 13 uses `0x450`; other checked sections use the footer length when valid and `0xFF4` otherwise. Section 4 is opaque and excluded from generic checksum validation. A checksum mismatch in an older fallback generation is not presented as a current-save warning.

The review separately shows warnings for the uploaded file and the proposed download. It compares the proposed bytes with an immutable upload snapshot and counts changed bytes per physical sector, separating payload and footer changes. Recognizable byte regions are labeled: Party count, Party slot nickname/level/data, stream PC box/slot fields, Preset slot fields, Battle Points, and Bag data. A label identifies the byte region that changed; it does not claim a decoded semantic value changed when bytes are encrypted or packed. Unmapped regions remain **Section data**.

The canonical scanner is `backend/modules/save_health.py`, with matching browser and native core scanners. Switch and 3DS retain an upload snapshot and can build the same core report, verified by `make test-save-health`. Neither native UI currently displays a review screen before saving; this is a documented presentation gap. Their existing phases 1–4 continue to verify save-data parity.
